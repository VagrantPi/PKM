## 🎯 什麼情境該想到我
當一個業務動作要跨多個服務/資料庫、卻無法用單機交易保證「要嘛全成、要嘛全敗」時。

## ⚙️ 怎麼用（依一致性需求選方案，沒有銀彈）
1. **可靠訊息佇列（本地訊息表 = Outbox）**：把業務寫入與事件記錄放同一本地交易，再由 relay 投遞 → 最終一致。最常用、最務實（見 [[工具-Transactional-Outbox-Pattern]]）。
2. **TCC（Try-Confirm-Cancel）**：業務層自己實作預留/確認/取消，強一致但侵入性高、開發成本大。
3. **Saga**：把長交易拆成一連串本地交易 + 對應的**補償動作**，失敗就反向補償。適合長流程。
4. **2PC/XA**：強一致但同步阻塞、協調者單點，效能差，少用於高併發。

先問：這個場景**需要強一致，還是最終一致就好**？多數選最終一致（1）。

### ★ 先問三個問題（多數情況根本不需要分散式事務）

```
① ★ 這兩件事真的必須在「不同的服務／資料庫」嗎？
   → 常常是切錯了邊界。同一個聚合內的東西不該跨服務（見 [[工具-限界上下文]]）

② ★ 真的需要「強一致」，還是「最終一致 + 使用者看得到狀態」就好？
   → 「下單後 3 秒庫存才扣」在業務上幾乎總是可以接受的

③ ★ 失敗時可以「人工處理」嗎？
   → 每天 3 筆異常 → 對帳報表 + 人工補償，★ 遠比建一套 Saga 框架划算
```
> ★ **最好的分散式事務是「不要有分散式事務」。**
> 大多數「需要分散式事務」的需求，實際上是**服務邊界切錯了**的症狀。

### ★ 四種方案的完整對照

| 方案 | 一致性 | 複雜度 | 可用性 | ★ 什麼時候用 |
|---|---|---|---|---|
| **★ Outbox（本地訊息表）** | 最終 | **低** | 高 | ★ **預設選這個**。90% 的場景 |
| **Saga** | 最終 | 中 | 高 | 長流程、多步驟、有明確的補償動作 |
| **TCC** | 準強 | **高** | 中 | 需要「預留資源」的場景（訂票、扣庫存） |
| **2PC / XA** | 強 | 中 | ★ **低** | **幾乎不要用**（見下） |

### ★ Outbox：為什麼它是預設答案

```
❌ 雙寫問題（dual write）
BEGIN; UPDATE orders ...; COMMIT;
kafka.Publish(event)          ← ★ 這裡掛掉 → 訂單建了但沒人知道

✅ Outbox
BEGIN;
  INSERT INTO orders ...;
  INSERT INTO outbox (event) VALUES (...);   ← ★ 同一個本地交易，要嘛都成功要嘛都失敗
COMMIT;
-- 背景 relay（或 CDC 讀 WAL）把 outbox 推到訊息佇列
```
★ **它的天才之處：把「跨系統的原子性」化約成「單一資料庫的本地交易」**，
而單一資料庫的交易是可靠的（見 [[工具-交易與隔離等級]]）。

**代價**：**至少一次投遞** → ★ **消費端必須冪等**（見 [[工具-MQ消費端防禦三原則]]）。

### ★ Saga：補償的設計才是難點

```
正向：  建訂單 → 扣款 → 扣庫存 → 出貨
補償：  取消訂單 ← 退款 ← 回補庫存 ← （已出貨無法補償）
```

**三件必須想清楚的事**：

| 問題 | 說明 |
|---|---|
| **★ 補償不等於回滾** | 退款 ≠ 沒扣過款（帳上留下兩筆紀錄、可能有手續費）。<br>**Saga 沒有「原子性」，只有「最終達到某個可接受的狀態」** |
| **★ 有些步驟不可補償** | 已出貨、已寄出的 email、已呼叫的第三方 API。<br>→ ★ **把不可逆的步驟排在最後**，或改成「可逆的形式」（延遲執行、草稿） |
| **★ 補償本身也會失敗** | 退款 API 也可能掛。→ **補償必須可重試 + 冪等 + 最終有人工介入的出口（dead letter）** |

**編排（orchestration）vs 協同（choreography）**：
| | Orchestration | Choreography |
|---|---|---|
| 流程在哪 | ★ **一個中央協調者**（看得到整條流程） | 散在各服務的事件監聽裡 |
| 好處 | ★ **流程可讀、可追蹤、易改** | 鬆耦合，沒有中心 |
| 壞處 | 協調者是新的耦合點 | ★ **沒有人知道完整流程長什麼樣** |
| 建議 | ★ **步驟 ≥ 3 就用編排** | 只有兩步時可以協同 |

### ★ 為什麼 2PC 幾乎不該用

```
協調者 → 「準備好了嗎？」→ 所有參與者鎖住資源並回「好了」
       ★ 此時協調者掛掉 → 所有參與者「永遠持鎖等待」（in-doubt）
       → 資源被鎖住，無法自行決定，必須等協調者回來
```
| 問題 | 說明 |
|---|---|
| ★ **協調者單點** | 它掛了，參與者全部卡住 |
| ★ **同步阻塞** | 整個 prepare→commit 期間所有參與者持鎖 |
| **可用性差** | 任一參與者不可用，整個交易失敗（可用性是各方的**乘積**） |
| **效能差** | 至少兩輪網路往返 + 持鎖時間長 |

★ **它在單一資料庫叢集內（同一個 DBMS 的多個分片）還算堪用；跨異質系統基本上是災難。**

### TCC 的三個坑（不處理就會出事故）
TCC 把兩階段搬到業務層：Try 預留資源、Confirm 確認、Cancel 釋放。網路亂序與重試會造成三種狀況：

| 坑 | 怎麼發生 | 不處理的後果 |
|---|---|---|
| **空回滾** | Try 因網路逾時沒到，全域事務逾時觸發 Cancel，Cancel 先到 | Cancel 直接「釋放資源」→ **把別人正常扣的名額或庫存加回去** |
| **懸掛** | 空回滾之後，遲到的 Try 才到並預留了資源 | 全域事務已經結束，這筆預留**永遠沒人 Confirm 或 Cancel** |
| **冪等** | Confirm／Cancel 因重試被呼叫多次 | 重複扣款、重複釋放 |

**解法是一張「分支狀態表」**，以全域事務 ID 加分支 ID 當唯一鍵：
- Try 前先插入一筆 `TRIED`；插入撞到唯一鍵，代表這個分支已經被回滾過 → 拒絕執行（防懸掛）。
- Cancel 時查不到紀錄（Try 沒執行過）→ 插入一筆 `SUSPENDED`，**不做任何釋放**（處理空回滾）。之後遲到的 Try 插入會撞鍵而被擋下。
- Confirm／Cancel 看到狀態已經是終態（`COMMITTED`／`ROLLBACKED`）→ 直接回成功，不重做（冪等）。

Seata 從 **1.5.0 起內建這套機制**（TCC fence，`tcc_fence_log` 表，原始碼 `SpringFenceHandler`），用 Seata 的話不必手寫；Go／Node 沒有現成框架時，照上面的狀態表自己實作。
（補充自 https://juejin.cn/post/7699427841725382707 ，查證 2026-10-24；原文說要自己寫事務紀錄表、業務程式碼會很沉重，沒有提到 Seata 已內建。）

### Seata AT 模式（Java 生態的「自動補償」）
不寫 TCC、也不建訊息表時的折衷，**只適用於關聯式資料庫**：
- **一階段**：資料源代理攔截業務 SQL，記下更新前後的資料鏡像，和業務資料**在同一個本地交易**寫進 `undo_log`，然後本地提交。
- **全域鎖**：提交前向協調者登記要改的列；全域提交時立刻釋放，全域回滾時要等分支二階段結束才釋放。
- **回滾**：讀 `undo_log` 產生反向 SQL 把資料改回去。

| 限制 | 影響 |
|---|---|
| 全域鎖 | 熱點列併發寫入時會退化成排隊，秒殺、大促這類場景撐不住 |
| SQL 解析不完整 | 複雜 SQL（例如多表 join 更新）可能產生不了 undo log，回滾失敗 |
| **每張表都要有主鍵** | 沒有主鍵就建不出前後鏡像 |
| **全域隔離等級預設是讀未提交**，最高只到讀已提交 | 別的交易可能讀到之後會被回滾的資料 |

（依據：Apache Seata wiki〈概覽〉與 `ConnectionProxy`、`TableMeta` 原始碼，查證 2026-10-24；主鍵與隔離等級兩項是原文沒寫的。）

### ★ 產品端要配合的事（技術解不了的部分）

最終一致性**必須在產品層面被承認**，不能偷偷做：
- ★ **顯示中間狀態**：「訂單處理中」而不是假裝已完成
- ★ **提供查詢入口**：使用者能看到目前進度
- **定義補償後的使用者體驗**：退款要通知、要說明原因
- ★ **對帳機制**：定期比對兩邊，**找出不一致並告警**——
  **這是最被忽略但最重要的一環。沒有對帳，你永遠不知道系統有沒有出錯。**

## ⚠️ 注意 / 什麼時候不適用

- **★★ 先檢討服務邊界**。頻繁需要跨服務事務 = 邊界切錯了（見 [[工具-服務邊界與演進式拆分]]）。
  **合併回同一個服務往往是正確答案**，而不是蓋一套 Saga 框架。
- **★ 一定要有對帳**。任何最終一致的系統都會飄移，**只是你知不知道。** 排定期對帳 + 告警 + 人工修補流程。
- **★ 消費端冪等不是可選的**。所有方案都是「至少一次」投遞。
- **不可逆的步驟要排在最後**，或延遲執行（見 [[可逆性、審計與人類把關]] 的 L3 降級技巧）。
- **Saga 的狀態要持久化**。流程執行到一半服務重啟 → **要能從中斷處續跑**（見 [[狀態模式]]）。
- **不要用「分散式鎖」代替分散式事務**。鎖不安全（見 [[工具-線性一致性與共識]] 的 fencing token）。
- **★ 測試很難**。要測「第 3 步失敗時補償有沒有正確執行」——**故障注入是必要的**（見 [[工具-注入故障與韌性演練]]）。
- **監控要能看到「卡住的 Saga」**：超過 N 分鐘還沒完成的流程要告警。
