## 📐 三份來源怎麼分工（重要，別讀錯輩分）

| 來源 | 回答什麼 | 變動速度 | 現況 |
|---|---|---|---|
| [[Effective Go]] | **Go 為什麼長成這樣**（心智模型） | 很慢 | ⚠️ 寫於 2009、官方明說不再更新。觀念成立，**Errors 章與並行寫法已過時** |
| [[Modern Go Guidelines]] | **現在該用哪個 API** | 很快 | 對照表，涵蓋 Go 1.0 → 1.27 |
| [[Google Go 風格指南]] | **兩種寫法都合法時選哪個** | 中 | Google 內部 readability 審查的依據；部分 API 為內部專屬 |

還有一份查證紀錄：[[Go Blog 經典六篇]] —— 六篇官方經典**逐篇對照現行文件**的結果（哪篇能信、哪一句不能）。

**建議順序**：Effective Go 建立直覺 → Modern Go Guidelines 更新語法 → Google 風格指南學取捨。

## ✍️ 命名與可讀性
- 命名跟其他語言哪裡不一樣、縮寫大小寫、getter 要不要加 Get → [[工具-Go命名慣例]]
- 兩種寫法都合法、review 吵不出結論、該不該引入新函式庫 → [[工具-Go可讀性五原則]]

## 🧩 型別與介面設計
- 介面該多小、定義在哪一邊、該用介面還是泛型 → [[工具-Go介面小而隱式]]
- 想省掉一堆轉發方法、嵌入到底是不是繼承 → [[工具-Go嵌入機制]]
- 函式參數越加越多、要不要上 functional options → [[工具-Go函式參數太多怎麼辦]]
- 想加 package 層級變數、註冊表或全域 client → [[工具-Go全域狀態的判準]]

## ❌ 錯誤處理
- **哨兵／型別／不透明怎麼選、`errors.Is`／`AsType`／`Join` 怎麼用** → [[工具-Go現代錯誤處理]]
- **`%v` 還是 `%w`、`%w` 放哪、誰負責記 log、對外要不要暴露內部錯誤** → [[工具-Go錯誤該包還是該轉]]

> ⚠️ 這兩張卡目前**內容與 triggers 有重疊**（包裝時機、重複 log），分工待重劃。暫時的區分：前者偏「錯誤值本身怎麼設計與判斷」，後者偏「往上傳時的包裝決策與邊界」。

- 懷疑有資料競爭但重現不了 → [[工具-用race偵測器抓資料競爭]]
