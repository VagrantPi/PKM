## 📌 30 秒摘要
> 「訂單 30 分鐘未付款怎麼自動取消？」答「寫個定時任務每分鐘掃資料庫」會被面試官嫌棄——不是錯，是笨重：**精度上限被掃描週期綁死**，而且多實例還要自己處理重複。正解是把**被動輪詢換成到點主動觸發**，三個方案：**Redis ZSet**（member=訂單號、score=到期時間，Lua 原子取出，預設選它）、**MQ 死信佇列**（緩衝佇列設 TTL → 過期成死信 → DLX 轉業務佇列，可靠性最高但同佇列 TTL 必須一致）、**時間輪**（純記憶體、插入 O(1)，Netty／Kafka 的作法）。追問鏈裡最值錢的一題：取消撞上付款，**別三步走，直接 `UPDATE ... WHERE status='UNPAID'` 用影響行數判勝負**。

## ✨ 關鍵重點

- **定時掃描的兩個指控，一個成立一個要打折**。
  - ✅ **精度**：誤差上界 = 掃描週期。12:00 下單、12:30 該取消，每分鐘掃一次就可能拖到 12:31，這一分鐘裡庫存鎖、優惠券、秒殺名額都被一張不會付款的單白佔著。要精度就得縮短週期，要省 DB 就得拉長——**兩者綁在同一個旋鈕上，這才是換方案的真正理由。**
  - ⚠️ **「全表掃描」要打折**：只要有 `(status, create_time)` 複合索引，那就是索引範圍掃，而且取消後訂單離開 `UNPAID` 前綴，待掃區間有界。「每分鐘犁三千萬行」多半是索引沒做好，不是方案的死罪。（原文這點講得偏重，我在工具卡裡修正了）
- **Redis ZSet**：`score = 下單時間 + 30 分鐘`，worker 盯最小 score。skiplist 取最小是 `O(log N)`，隊伍裡只有未到期的單，天生沒有無效資料。**取出必須用 Lua 把 `ZRANGE BYSCORE` + `ZREM` 包成原子**，否則多實例重複消費。
  - 原文用的 `ZRANGEBYSCORE` 自 **Redis 6.2 起已 deprecated**，新寫法是 `ZRANGE key 0 now BYSCORE LIMIT 0 1`。
  - 原文沒提的洞：**`ZREM` 成功後、業務執行完前 crash，任務就消失了**。要補成 visibility timeout 兩階段（搬到 processing set，做完才 ack）。
- **MQ 死信佇列**：緩衝佇列不掛消費者＋設 TTL → 過期成死信 → DLX 路由到業務佇列。業務程式碼最乾淨、可靠性最高。**前提是同一佇列裡所有訊息 TTL 一致**，因為 per-message TTL 只在訊息走到隊首才被檢查，混用會造成隊頭阻塞。多級延遲 → 多組佇列／`x-delayed-message` 外掛／RocketMQ（4.x 只有 18 個固定延遲等級，5.x 才支援任意時間）。Kafka 無原生延遲訊息。
- **時間輪**：`slot = (cur + d/T) % S`、`circle = (d/T) / S`，指針每繞一圈把該格任務圈數減 1，減到 0 才執行。插入是 `O(1)`（鏈結串列 append，不排序）。
  - **但「取出也 O(1)」是半真**：單層＋圈數的版本，每個任務在到期前會被空摸 `d/(S×T)` 次。我實測 20 萬個 30 分鐘任務、60 格 × 1 秒錶盤 → 每任務被摸 **30.0 次**，和公式吻合。真正攤還 `O(1)` 的是**階層時間輪**（Kafka 用這個；Netty `HashedWheelTimer` 是單層＋圈數）。
- **追問一｜Redis 掛了訂單就永遠不取消？** 定時任務沒死，只是降級成**低頻小窗口對帳**：每 10 分鐘掃一次「建立時間落在 30～40 分鐘前」的窄區間走索引，不是全表犁地。
- **追問二｜取消和付款撞在一起？** 別「查出來 → 判斷 → 更新」三步走，那中間有 TOCTOU 窗口。直接 `UPDATE orders SET status='CANCELED' WHERE id=? AND status='UNPAID'`，**影響行數 0 就代表已被付款回呼改掉，放棄取消**。行鎖幫你判勝負，不必加分散式鎖。
- **追問三｜時間輪精度怎麼定？** 訂單超時是秒級需求，tick 1 秒 × 60 槽就夠。要毫秒級請上階層時間輪，別把單層 tick 硬壓小（會讓圈數暴增到幾千圈）。
- **選型結論**：預設 Redis ZSet（夠簡單、夠準、延遲長度任意）；日均千萬單、對可靠性有硬要求再上 MQ；時間輪留給「單機、不想多一個依賴、量體大」。真實專案常常混用：**Redis 扛主流程，定時任務做對帳兜底。**

- 「這不是錯，是笨重。」
- 「把笨重的被動輪詢，換成基於事件的主動觸發。」
- 「誰 ZREM 成功誰負責執行。」
- 「定時任務是兜底，不是方案；主動觸發才是方案。」
